# Administrative I/O and apparent cold starts: 2026-11-16

Production search delays were not all machine starts: the reader had been up
for more than four days. During stalled health requests, a captured kernel stack
showed a Tokio HTTP worker in `pread64` on descriptor 9, the mutation SQLite
file, at offsets around 1.3 GB. Other runtime threads were parked, and health
connections queued on the listener. The mutation database was 1.7 GB; memory and
I/O pressure were high and the VM's 512 MB swap was full. These observations
identify blocking database reads on the HTTP runtime as a concrete failure;
they do not establish that every slow request has the same cause.

## Fix

- Run synchronous administrative reads on `spawn_blocking`, following the
  existing mutation-handler boundary. Authorization and page validation remain
  before dispatch; responses and error mapping remain unchanged.
- Add a covering `(video_id, youtuber_id, chunk_count)` index for ordered bulk
  inventory reads. Summaries follow a large `chunks_json` BLOB in the table;
  reading their original rows can traverse overflow pages and evict search data.
- Add a partial index for the existing missing-summary predicate. Reopening an
  already-backfilled store can check that small index. Legacy backfill and
  tombstones retain their existing behavior.
- Send browser `request_duration_ms` and `edge_cached` to PostHog. Omit the
  original backend timing on edge hits, where it describes the cached response's
  original computation rather than the current request.

The bulk merge still sees all mutation summaries: filtering only by the current
creator would lose removals when videos move or are deleted. Per-video equality
lookups remain unchanged; SQLite can prefer their unique primary-key index.
Read-only older snapshots need no new indexes. No index schema, chunks, ranking,
creator counts, cache TTL, or production resources change.

## Evidence

A real TCP/router regression on a single-thread Tokio runtime holds the store
mutex from an OS thread and sends an authenticated admin read followed by health.
The old handlers fail because health waits for the externally bounded two-second
watchdog. The fixed handlers answer health while that lock is still held.

A Rust SQLite fixture uses 128 completed summaries with 64 KiB chunk bodies,
an eight-page connection cache and mmap disabled. Actual bulk-summary and
completed-startup reads each require fewer than 24 SQLite cache misses. An
independent `NOT INDEXED` negative control returns identical summaries but
requires more than 128 misses. Query plans verify the bulk covering index;
a literal legacy schema verifies backfilled metadata, unchanged chunk bytes,
tombstones, and repeated-open idempotence.

A separate local 256 MiB SQLite fixture with 1,024 rows and five trials measured:

| Operation | Before median | After median |
| --- | ---: | ---: |
| Bulk summaries | 53.177 ms | 0.249 ms |
| Completed-store missing-summary probe | 0.089 ms | 0.003 ms |

The result rows match independently enumerated metadata. This is a local
SQLite microbenchmark, not a production API or browser latency claim. Python's
SQLite was 3.54.1; the Rust tests exercise the repository's bundled SQLite.
Initial construction of both indexes took 41.6 ms on that local fixture.

## Full-reader HTTP replay

Both release readers served the same 8,142,650-document schema-9 index, with
four P-cores each and the driver on low-power cores. Separate mutation-store
fixtures had 1,024 completed summaries and 256 KiB chunk bodies per row. The
baseline had no auxiliary indexes; the candidate created them through its normal
writable open. Each trial starts 16 concurrent authenticated channel-inventory
requests, then probes health and an uncached `react` search after the first
inventory response. Five trials per binary were repeated with the replay order
reversed. Other repository checks ran in the background, so absolute local
latency is contextual.

| Replay order | Health before / after median | Search before / after median |
| --- | ---: | ---: |
| Baseline first | 864.06 / 0.84 ms | 723.01 / 19.67 ms |
| Candidate first | 1,048.97 / 0.45 ms | 1,067.61 / 18.38 ms |

All returned search payloads matched after excluding timing fields. Every
inventory response independently matched 147 videos and 75,264 chunks, computed
from the fixture's enumerated metadata. This exercises real HTTP serving,
SQLite reads and search execution together; it is still local verification,
not a post-deployment browser E2E result. The workload script and both raw JSON
runs are in the artifact directory below.

## Release considerations

Index construction is idempotent, but the first upgraded writable open must
scan the existing table to build them. That one-time cost is distinct from
subsequent startup improvement. Production's larger, slower-volume migration
must be timed in isolation; do not restart an active publisher or weaken
snapshot/checksum validation to make the first upgrade appear faster.

Reproduction artifacts, kernel stacks, production inventory, source designs,
query plans, fixture script and measurements are under
`/home/pronsh/.cache/ytsearch-coldstart-20261116/`. This change does not by itself
prove the user's 300 ms browser end-to-end objective. That requires post-release
cache-miss and cache-hit measurements including network and browser rendering.

## Verification

`bun run check` passed, including `bun run check:precommit`, workspace Rust tests,
all 23 browser scenarios, dependency/license/public-surface checks and operational
fixtures. Ten mutation-store tests, eleven admin tests and three analytics tests
passed. The existing handler code failed the new bounded health regression;
the candidate passed. Both HTTP replay orders preserved search payloads and
independently checked inventory counts. Production recovery remains unverified
until an approved release and post-release measurements.
